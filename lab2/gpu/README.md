# Часть 6. GPU vs CPU — какой трек выполнен

## Выбран: Трек A (обязательный, локально на CPU)

**Выполнен Трек A** — сравнение CPU-движков **pandas (однопоточный) vs Polars (многопоточный,
Arrow) vs DuckDB (векторизованный SQL)** на одинаковых объёмах (100 МБ и 1 ГБ) и одном контракте
задачи (`GROUP BY Attack × Attack_subType × Device_Name`, count + 2×avg + max). Метрики, код и
замеры — общие с частью 2 (один и тот же прогон, без пересъёмки): таблица в ноутбуке (раздел
«Часть 6»), сырые строки — `lab2/results/track_a_table.csv` и `lab2/results/engines_all_measurements.csv`.

Результат в двух строках: Polars и DuckDB на 1 ГБ быстрее Pandas в разы при тех же лимитах
потоков; главный драйвер — многопоточное стримящее чтение CSV и векторные агрегаты вместо
однопоточного парсинга в объектную модель. Числа — в ноутбуке, они вычисляются из замеров.

## Трек B (cuDF for Apache Spark) — НЕ запускался, честные причины

Оборудование машины: NVIDIA **GeForce RTX 3050 Laptop, 4 ГБ VRAM** (драйвер nvidia-smi 621.14,
CUDA Toolkit 12.x совместим). Формально GPU есть, но условия трека не выполнены:

1. **Среда.** cuDF for Apache Spark распространяется как Spark-плагин в Linux/Docker-образах
   (NVIDIA/spark-rapids-images, многорабочие гигабайты). На Windows это только WSL2 + Docker
   Desktop + GPU runtime; reproducible-окружение лаборатории (venv + `local[2]` + Windows)
   так не воспроизводится, а требование «запускаемый с нуля ноутбук» было бы нарушено.
   Уточнение: WSL2 и Docker Desktop на этой машине установлены, так что путь технически
   возможен — отказ от него держится на пунктах 2–3 (VRAM и экономика), а не на «нет GPU»:
   сам GPU (RTX 3050, 4 ГБ) в машине есть и работает.
2. **Ресурсы.** 4 ГБ мобильной VRAM — пограничный объём для Spark-on-GPU: служебные буферы
   (GPU-кэш и spill) съедают гигабайты до полезной работы.
3. **Экономика (главное).** По материалам задания точка окупаемости GPU-плагина — запросы
   от ~30 с: инициализация executor/GPU ~2–3 с, передача данных между CPU/GPU. Наша контрактная
   агрегация полного датасета на CPU (Spark, local[2]) укладывается в десятки секунд, а Polars/DuckDB
   на 1 ГБ — в секунды. Ожидаемый выигрыш трека B на этой задаче и этом железе — отрицательный
   или статистически ничтожный, и было бы нечестно заявлять «GPU-ускорение» по такому прогону.

**Как бы выглядел прогон B (для воспроизводимости решения):** образ
`nvcr.io/nvidia/spark-rapids-ml` (или base-плагин `spark353-gpu`), запуск в WSL2/Docker с
`--gpus all`, те же parquet-входы, `spark.rapids.sql.*`, те же метрики wall/RAM(IO)/профили
стадий. Тест «когда GPU не окупается» (пункт 3 задания) закрывается расчётом выше + меренными
CPU-временами — обе части (ускорение и границы применимости) в работе присутствуют.

## Трек C (облачный GPU-фолбэк) — не использовался

Требует внешнего аккаунта (Colab/Kaggle) и ручной загрузки 1 ГБ+ данных; по заданию треки B/C
опциональны, «оценивание одинаково для всех треков», обязательный вклад — Трек A. Он выполнен.
